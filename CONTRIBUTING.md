# Contributing

Thanks for helping. Bug reports, missing endpoints and fixes are all welcome.

## How the repository fits together

`spec/` describes the API; `tools/codegen` turns it into models and resources for every SDK;
the handwritten core of each SDK (authentication, transport, pagination, streaming) lives next to
the generated code. [docs/development/architecture.md](docs/development/architecture.md) has the
details and the rules every SDK follows.

Generated files start with `Code generated by whitebird-codegen. DO NOT EDIT.` Change the spec or
the emitter instead, then regenerate:

```sh
cd tools/codegen
uv run python -m whitebird_codegen generate            # every language
uv run python -m whitebird_codegen generate --lang go  # one language
```

The generator needs `ruff` (through uv), `npm ci` in `node/`, `gofmt` and `rustfmt`.

## A new or changed endpoint

1. Describe the endpoint in `spec/services/<service>.yaml` (see the conventions in the
   architecture document). Mark it `x-wb-status: experimental` while its response shape is not
   confirmed.
2. Regenerate and run the checks below.

Please do not send requests with real accounts to Whitebird from tests; every test runs against a
local mock server.

## Checks

| Directory | Commands |
|---|---|
| `python/` | `uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest` |
| `node/` | `npm ci && npm run typecheck && npm run lint && npm test` |
| `go/` | `gofmt -l . && go vet ./... && go test -race ./...` |
| `rust/` | `cargo fmt --check && cargo clippy --all-targets --all-features && cargo test --all-features` |
| `tools/codegen/` | `uv run pytest && uv run python -m whitebird_codegen generate --check` |
| docs | `bash scripts/docs-reference.sh && pip install -r docs/requirements.txt && mkdocs serve` |

## Commits and releases

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org) with the
package as scope: `feat(python): ...`, `fix(go): ...`, `feat(spec): ...`. release-please uses them
to propose the next project version and the changelogs; [publishing](docs/development/publishing.md) explains the
release process.
