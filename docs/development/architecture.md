# Architecture

The repository holds four SDKs (Python, Node.js, Go, Rust) generated from one description of
the Whitebird API. Whitebird does not publish an API reference, so that description is
reconstructed from the public web application and kept up to date by an automated drift check.

```
spec/                     source of truth
  environments.yaml       service hosts per environment, OAuth client
  services/<service>.yaml one OpenAPI 3.1 document per backend service
tools/
  wbscan/                 extracts endpoints from the whitebird.io bundles, diffs them with spec/
  codegen/                turns spec/ into models and resource classes for every language
python/ node/ go/ rust/   SDKs: handwritten core + generated layer
```

## Pipeline

1. `wbscan scan` downloads the current frontend build, deobfuscates it with webcrack and extracts
   every HTTP call into `inventory.json`.
2. `wbscan diff` compares the inventory with `spec/` and reports new, removed and changed endpoints.
   The scheduled `api-drift` workflow runs it daily and opens an issue when the API moves.
3. The spec is updated (imported from a public OpenAPI document where one exists, written by hand
   from the inventory otherwise).
4. `codegen` regenerates the SDKs. CI fails if generated files are out of date.

## Spec conventions

Every file in `spec/services/` is a self-contained OpenAPI 3.1 document. Paths are absolute from
the host root (`/api/v1/...`). Whitebird-specific metadata lives in `x-wb-*` extensions.

Document level:

| Key | Meaning |
|---|---|
| `x-wb-service` | Service key from `environments.yaml` (`trading`, `auth`, ...) |

Operation level:

| Key | Required | Meaning |
|---|---|---|
| `operationId` | yes | camelCase, unique across all services |
| `x-wb-resource` | yes | Dotted namespace on the client, e.g. `orders` or `brokerage.otc_orders` |
| `x-wb-name` | yes | Method name in snake_case, unique within the resource |
| `x-wb-auth` | no | `user` (default, bearer token), `none` (public), `mfa` (needs an operation MFA token) |
| `x-wb-status` | no | `stable` (default), `experimental`, `deprecated` |
| `x-wb-source` | no | `openapi`, `bundle` or `live`: where the shape comes from |
| `x-wb-first-seen` | no | Date the endpoint first appeared in a scan |
| `x-wb-response` | no | `json` (default), `binary`, `text`, `empty`, `sse` |
| `x-wb-envelope` | no | Response wrapper to unwrap; also allowed at document level (see below) |

Most services answer with the payload directly. Market data answers with a Bybit-style envelope
`{"retCode": 0, "retMsg": "OK", "result": ...}`; such operations are marked
`x-wb-envelope: retcode`, the response schema describes `result` only, and the client unwraps it,
raising `APIError` (with `code = retCode`, `message = retMsg`) when `retCode` is not 0.

Numbers without a `format` are treated as decimals: Springdoc renders Java `BigDecimal` that
way, and on an exchange they are amounts, prices and rates. `format: double` or `float` marks a
plain floating-point number.

Schema properties may carry `x-wb-inferred: true` when the field was inferred from how the web
application uses the response rather than observed on the wire. Inferred fields are never
`required`.

Pagination is detected from the response schema: an object with `content` (array) and
`totalElements` is a Spring Data page. Paginated operations take `page`/`size` (query or body)
and are exposed as auto-paginating iterables (see below). Page wrapper schemas are not generated
as models; every SDK has one generic `Page` type.

## Generated vs handwritten code

| | Generated (never edit) | Handwritten core |
|---|---|---|
| Python | `python/src/whitebird/_generated/` | everything else in `python/src/whitebird/` |
| Node | `node/src/generated/` | everything else in `node/src/` |
| Go | `go/*_gen.go` | other `go/*.go`, `go/otp/` |
| Rust | `rust/src/generated/` | everything else in `rust/src/` |

Generated files start with the standard marker (`Code generated by whitebird-codegen. DO NOT EDIT.`).

The generator builds a language-neutral intermediate representation (IR) from the spec
(`tools/codegen/src/whitebird_codegen/ir.py`) and passes it to one emitter per language
(`emitters/<lang>.py` + `templates/<lang>/`). `python -m whitebird_codegen dump-ir` prints the IR
as JSON.

## Client design

The public surface is the same in every language; only the idioms differ.

### Construction and environments

A client is built from credentials and an environment (`production` by default, `demo` for the
sandbox trading contour). Each service base URL can be overridden individually, so a service
moving to a new host does not require a release.

### Resources

Operations are grouped into nested resources following `x-wb-resource`:
`client.market.orderbook(...)`, `client.brokerage.otc_orders.create(...)`.

Method parameters:

- path parameters are positional and required, in path order;
- query and body fields are passed as named arguments (Python keyword-only arguments, a params
  object in TypeScript, a params struct in Go and Rust);
- every method accepts per-request options (timeout, extra headers, idempotency of retries).

### Pagination

A paginated method returns an object that is directly iterable over items and fetches the next
page lazily:

```python
for order in client.orders.history(size=50):
    ...
async for order in async_client.orders.history(size=50):
    ...
```

```ts
for await (const order of client.orders.history({ size: 50 })) { ... }
const firstPage = await client.orders.history({ size: 50 }); // Page<Order>
```

```go
for order, err := range client.Orders.History(ctx, whitebird.OrdersHistoryParams{Size: 50}) { ... }
page, err := client.Orders.HistoryPage(ctx, params)
```

```rust
let mut orders = client.orders().history(params);   // impl Stream<Item = Result<Order>>
while let Some(order) = orders.try_next().await? { ... }
```

Single pages with metadata (`total_elements`, `total_pages`, ...) stay available in every
language.

### Authentication

- OAuth2 password grant at `auth` `/oauth/token`, form-encoded, `Authorization: Basic <oauth.basic>`.
  Fields: `grant_type=password`, `username` (lowercased), `password`, optional `code` (TOTP).
- `POST /api/v1/client/mfa {"username": ...}` on `auth` returns `{"mfaEnabled": bool}`; the web
  app uses it to decide whether to ask for a code.
- A 200 response without `access_token` but with `mfaEnabled: true` means a code is required.
- Refresh: same endpoint, `grant_type=refresh_token`, `refresh_token=...`. The client refreshes
  proactively when the JWT `exp` is less than 30 s away and reactively once on a 401. If refresh
  fails and a password is known, it logs in again.
- Login is lazy (first authenticated call) and can be triggered explicitly.
- Tokens are kept in a pluggable token store (in-memory by default) so sessions survive restarts.
- TOTP codes come from a code provider: a static code, a callback, or the `otp` extra that
  computes codes from the base32 secret.
- Operation MFA: sensitive operations (withdrawals) need an MFA token sent as `x-mfa-token`.
  The client stores it once obtained and attaches it to every request.
- Every request sends `Authorization: Bearer <token>` unless the operation is `x-wb-auth: none`.

### Errors

Whitebird services answer errors as `{"code": int, "status": "MACHINE_CODE", "message": str,
"fields": [...]}`; the OAuth endpoint answers `{"error": ..., "error_description": ...}`.

```
WhitebirdError
├── TransportError                 network failure, timeout
└── APIError                       http status, code, error_code (status string), message, fields, raw body
    ├── BadRequestError            400
    │   └── VerificationRequiredError   status SMS_VERIFICATION_REQUIRED / LIVENESS_VERIFICATION_REQUIRED
    ├── AuthenticationError        401, invalid_grant
    │   └── MFARequiredError       login needs a TOTP code, or "requires mfa checking" / MFA_CHECKING_REQUIRED
    ├── PermissionDeniedError      403
    ├── NotFoundError              404
    ├── ConflictError              409
    ├── RateLimitError             429, retry_after
    └── ServerError                5xx
```

### Retries and timeouts

Idempotent requests (GET, HEAD, PUT, DELETE) are retried on connection errors, 429, 502, 503 and
504 with exponential backoff and jitter, honouring `Retry-After`. Default: 2 retries, 30 s
timeout. POST is never retried automatically.

### Tolerance to API changes

- Unknown response fields are ignored (Python keeps them in `model_extra`).
- Enums are open: unknown values are preserved instead of failing.
- Timestamps accept RFC 3339, naive ISO-8601 (treated as UTC) and epoch milliseconds.
- Decimal amounts are lossless where the language allows it.
- `client.request(service, method, path, ...)` calls any endpoint with the same auth, retries and
  error handling, for endpoints not yet in the SDK.

### Streaming

Notifications are delivered over Server-Sent Events (`notification` `/api/v1/sse/connect`, bearer
auth). Each SDK exposes them as a native stream (Python iterator / async iterator, TS async
iterable, Go `iter.Seq2`, Rust `Stream`) with automatic reconnect using `Last-Event-ID`.
